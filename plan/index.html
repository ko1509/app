2-3. 「直前に検索が集中する」性質を活かした更新ルール

検索は「イベント当日〜3日前」に一気に増え、終わると急に減る（推測：Googleトレンドで「ふたご座流星群」「H3 打ち上げ」を見るとこの形。公開後に自分のSearch Consoleで確かめる）。だから公開は早く、更新は直前に厚くする。

種類 初回公開 理由

タイミング やること

ルール3：延期への対応（ロケット特有）

  • 延期が発表されたら：①冒頭の状況ラベルを「延期」に ②新しい日時（未定なら「未定」） ③更新時刻 ④Event スキーマの eventStatus を更新 ⑤Xで告知（「延期になりました。宿のキャンセル・延長の考え方はこちら」）
  • 延期が続く打ち上げほど検索が長く続くので、延期の歴史（いつ・なぜ延期されたか）を時系列でまとめる節を付けると他サイトとの差になる。

ルール4：毎年くり返すイベントは「同じURLを毎年更新」

  • 流星群は /sky/geminids/（年なし）を毎年更新する（評価を積み上げられる）。年ごとの記録は記事内の「過去の観測記録」に追記する。号機や年を入れたURLは、1回限りのもの（特定の打ち上げ・彗星）にだけ使う。

ルール5：確認日時の表示を義務にする

  • すべての記事の冒頭に「最終確認：YYYY-MM-DD HH:MM（出典：○○）」を出す。
  • 事実が変わりやすいもの（運行時刻・打ち上げ日時）は公式URLを2つ以上付ける。
  • 推測には必ず「推測」ラベル。

ルール6：AIでの下書き作業を定型化する

  1. リサーチ用プロンプト（イベント名＋公式URLを入力 → 日時・場所・出典の表を出させる）
  2. 構成用プロンプト（テンプレートA/B/C＋表 → 見出しと本文の下書き）
  3. 事実確認（人がやる）：日時・料金・予約の要否だけは必ず公式ページで目視確認。AIの出力をそのまま公開しない
  4. 更新用プロンプト（公式の新しい発表文を貼る → 差分だけ書き換えた案と「更新履歴」の1行を出させる）

6-1. ミアゲタビの記事は「何をする記事」か

読んだ人が、その日・その時刻・その場所で、迷わず動けるようにする記事。

ふつうの解説記事と違い、読者はこのあと実際に動く（夜中に起きる、島へ飛ぶ、寒い場所で待つ）。だから誤りの損失が大きい。

誤りの種類 読者の損失 例
時刻・日付の誤り 見逃す 世界時を日本時間に直し忘れる。「15日未明」を15日の夜と書く。曜日の取り違え
状況の古さ 無駄足・宿代 延期が発表されたのに「予定どおり」のまま
見え方の誇張 がっかり・信頼を失う 「1時間に100個」（暗い空の理論値）を街中でも見えるように書く。日本で見えない日食を見えるように書く
場所の誤り 入れない・危ない 立入禁止区域や私有地を見学場として紹介する。駐車場がない場所に車で行かせる
安全の抜け けが・事故 日食を直接見る。夜道・寒さ・交通規制

→ 品質の第一は「時刻・場所・状況が正しく、確かめた日時が書いてあること」。 文章のうまさは二の次。

6-2. 質を決める8つの柱

柱1　時刻の正しさ（このサイトでいちばん大事）

  • 時刻は日本時間（JST）だけで書く。世界時（UT）の資料（NASA・IMOなど）は、コードで変換してから使う。暗算しない。
  • 曜日はコードで出す（python3 -c "import datetime; ..."）。曜日の書き間違いは信頼を一番落とす。
  • 「未明」「深夜」は日付があいまいになる。「14日（月）の夜から15日（火）の明け方」のように、夜をまたぐ時間帯は2つの日付で書く。
  • 打ち上げは「打ち上げ予定時刻」「打ち上げ時間帯（ウィンドウ）」「予備期間」を分けて書く。
  • 本文に相対日付（「今週末」「来月」「今年の」）を書かない。タイトルに入れる「今夜」「明日」は直前更新のときだけ。

柱2　一次情報と確認日時

  • 根拠の優先順位： 1. 当事者：JAXA、スペースワン、インターステラテクノロジズ、各施設 2. 自治体：南種子町、肝付町、串本町、大樹町、鹿児島県など 3. 国立天文台（ほしぞら情報・暦計算室） 4. NASA、IMO（国際流星機構） 5. 報道 6. その他（まとめサイト・個人ブログは根拠にしない）
  • 記事の冒頭に「最終確認：YYYY年M月D日 H:MM」を出す（プラグインの最終確認欄）。打ち上げの記事は、書いた時点でもう一度公式の状況を確かめる。
  • 確かめられない数字・事実は書かない。 「要確認」と添えて書くのも不可（KOAlil と同じ決まり）。
  • 例外として「編集部の目安」は書いてよい。ただし、確かめた事実から導いた理由を必ず添える。
  • 例：「交通規制が3時から始まると町が発表しているので、2時までに着くのが目安です」

柱3　「どう見えるか」を具体的に（情報利得の中心）

ほかのサイトにない価値は、読者の場所から何がどう見えるかを具体的に言えること。 - 天体：主な都市（札幌・東京・大阪・福岡・那覇）での方角と高さ（地平線から何度）を、見ごろの時刻についてコードで計算し、国立天文台の記述と食い違わないか確かめる（計算の道具は ops/sky.py）。 - 月明かり：月の出・月の入り・月齢をコードで出し、「何時から何時は月がなく暗い」と書く。 - 見える数：「暗い空での目安」と「街明かりのある場所の目安」を分ける。出典のある数字だけを使い、街中の数に出典がなければ書かない（「街中ではかなり減ります」と言うにとどめる）。 - 打ち上げ：見学場ごとに「射点（発射台）から何km」「射点が見えるか（山に隠れるか）」「ロケットが飛ぶ方向」を書く。遠くの都市から見えるかは、公式の案内か過去の実績（報道・公式の写真）があるときだけ書く。

柱4　動くための情報（ロジスティクス）

各記事に、少なくとも次のうち該当するものを入れる。 - 当日のタイムライン（何時に出て、何時に着き、何時に始まり、何時に帰れるか） - 交通（便の時刻・本数、レンタカーの台数、規制）と宿（埋まりやすさ） - 延期・中止・曇りのときの動き方（予備日をどう押さえるか、どこで情報が出るか） - 持ち物（季節と時刻に合わせる） - 天気の確かめ方（どのサイトの何を見るか）

柱5　初めての人に読める文章

  • 中学生が読んでわかる言葉で書く。専門用語は使わないか、出てきた最初の1回だけ一言で言い換える。
  • 極大 → いちばん多く流れる時間帯
  • 放射点 → 流れ星が飛び出してくるように見える点
  • 射点 → 発射台
  • 衝 → 一晩中見える時期
  • 等級 → 明るさ（小さいほど明るい）
  • 各見出しの最初の1〜2文で答える（アンサーファースト）。理由や背景はそのあと。
  • 1文はおおむね40字以内。二重否定を使わない。
  • 表は3列まで、セルは短く（スマホで読める幅）。説明は表の外に書く。
  • 「美しい天体ショー」「一生に一度」「圧巻」のような中身のない飾りを書かない。

柱6　体験の誠実さ

  • 行っていない・見ていないのに、行った・見たように書かない（体験の偽装は公開を止める誤り）。
  • 運営者の体験が入る記事だけ、体験記入欄 [体験記入: 何を書くか] を置く（依頼で「体験を入れる」を選んだときだけ）。
  • 写真は、運営者が撮ったものか、利用規約で使える公式の画像だけ。AIで作った画像を実際の写真のように使わない（図・イラストは「図」と明記する）。

柱7　安全と配慮

  • 日食：太陽を直接見ない・日食グラスの注意を冒頭に（この期間は日本で見える日食はないが、海外遠征の記事では必須）。
  • 夜：私有地・立入禁止区域に入らない。暗い道・寒さ・車の運転・駐車マナー。
  • 打ち上げ：射点の周り3kmは当日立入禁止（JAXA）。交通規制に従う。ドローンを飛ばさない。
  • エネルギー・原子力の話題は扱わない（サイトの決まり）。

柱8　収益化の節度

  • アフィリエイトは、読者がその場面で本当に必要なもの（宿・交通・三脚・防寒）だけ。記事の流れの中で、必要な理由と一緒に置く。
  • 値段・在庫・ポイントを本文に書かない（変わるため）。広告を含む記事はPR表記。
  • 「今すぐ予約しないと売り切れ」のような煽りを書かない。

6-3. どの記事にも入れる「ミアゲタビならではの要素」

記事ごとに、次のうち2つ以上を入れる（査読で確かめる）。 1. 計算した方角・高さ・時刻（複数の都市） 2. 当日のタイムライン 3. 延期・曇りのときの動き方 4. 見学場・観察場所の比較表 5. スマホの具体的な設定（機種別） 6. 過去の実績（前回の延期の経緯・混雑の報道など。出典つき）

6-4. AIが書くときに起きやすい失敗（査読で必ず見る）

失敗 防ぎ方
世界時のまま書く／変換を間違える コードで変換。出典の時刻系（UT・JST）を報告に書く
曜日の誤り コードで出す
「毎年○日」と決めつける その年の公式ページで確かめる
ZHR（理論値）を実際に見える数として書く 「暗い空での目安」と明記。出典の数字だけ
見えない現象を「見える」と書く（日本で見えない日食、半影月食） 国立天文台・NASAで日本からの見え方を確かめる
見学場・駐車場・トイレの捏造 自治体・JAXAの案内にあるものだけ
H3とH-IIA、号機・ミッション名の取り違え JAXAの特設ページで照合
延期後の古い日時が残る 書いた時点で公式の状況を再確認。冒頭の状況欄を必ず埋める
旅行の決まり文句（「絶景」「一生に一度」） 柱5のとおり削る
根拠のない一般化（「多くの人が」「いつも混む」） 出典があるときだけ。なければ確かめ方を書く

サイトマップが404のとき（上から順に試す）

  1. 設定 → 表示設定：「検索エンジンがサイトをインデックスしないようにする」にチェックが入っていないことを確認する（入っているとサイトマップは止まる）。
  2. 設定 → パーマリンク：何も変えずに「変更を保存」を押す（URLの決まりを作り直す）。
  3. サーバーやSWELLのキャッシュを削除して、https://miagetabi.space/wp-sitemap.xml を開き直す。
  4. それでも404なら、サイトマップ専用のプラグイン（例：XML Sitemap & Google News）を入れて、そのサイトマップのURLを Search Console に送る。WordPress標準のサイトマップを止めているプラグインがある可能性もある（推測）。

SWELLとSEOの関係（先に結論）

SWELLはSEOに有利です。ただし有利なのは「土台」の部分で、検索順位を決めるのは記事の中身です。

SWELLがやってくれること（自分で作らなくていい部分）： - 表示が速い：ページの速さは検索順位の要素の1つ。SWELLは軽く作られていて、「高速化」の設定（キャッシュ・遅延読み込み）も付いている。 - HTMLの構造が正しい：見出し（h1〜h3）の使い方が正しく、Googleが内容を読み取りやすい。 - 構造化データ：記事（Article）とパンくずの構造化データを自動で出す。 - 目次・パンくず・関連記事：読む人が迷わず、サイト内をめぐってもらいやすい（滞在時間・内部リンク）。 - 更新日の表示：このサイトは直前に何度も更新するので、検索結果やページに「更新日」が出るのは大きい。 - スマホ表示：スマホで読みやすい。Googleはスマホ版のページを基準に評価する。

SWELLだけではできないこと： - 記事の中身：検索した人の疑問（いつ・どこで・どうやって）に、どこよりも早く正確に答えること。順位はほぼここで決まる。 - イベントの構造化データ：SWELLが出すのは「記事」の情報だけ。打ち上げ日・状況（延期など）は、自作プラグイン miagetabi-core で Event として出す。両方出してもぶつからない。 - 更新の速さ：延期が発表されたら30分以内に直す、という運用。

SWELLと一緒に入れないほうがいいプラグイン（機能がかぶって遅くなる・表示が崩れる）：All in One SEO、Yoast SEO、Autoptimize、Jetpack、各種キャッシュ系（サーバーのキャッシュとSWELLの設定で足りる）など。SEOの設定は SWELL 開発元がすすめる SEO SIMPLE PACK を使う。

ステップ1　ドメインとサーバー（30分）

  1. サイト名とドメインを決める → 決定：ミアゲタビ／miagetabi.space。ドメイン・X・Instagramの3つが取れるか、同時に確かめる。
  2. レンタルサーバーの管理画面で、ドメインを追加する。
  3. 無料SSLをオンにする（URLが https:// になる）。
  4. サーバーの「WordPress簡単インストール」で WordPress を入れる。 - ユーザー名は admin などの推測されやすいものを避ける。 - 「キャッシュ自動削除」「データベース名」などはサーバーの初期値でよい。

サーバーの種類（エックスサーバー・ConoHa WINGなど）によって画面の名前は少し違う。わからないところがあれば、サーバー名を教えてくれれば手順を合わせます。

ステップ2　SWELLを入れる（15分）

  1. SWELLの会員サイト（SWELLERS'）から、親テーマと子テーマをダウンロードする。
  2. 管理画面 → 外観 → テーマ → 新規追加 → テーマのアップロード で、親テーマ → 子テーマの順に入れる。
  3. 子テーマを有効化する（カスタマイズは子テーマに入れると、SWELLを更新しても消えない）。
  4. 管理画面 → SWELL設定 → アクティベート で、SWELLERS' に登録したメールアドレスで認証する（認証しないとアップデートが受け取れない）。

ステップ3　初期設定（30分）

SSHが使える場合（おすすめ・5分）

  1. site/dist/miagetabi-core.zip と site/setup-wpcli.sh を、WordPressのフォルダ（wp-config.php がある場所）にアップロードする。
  2. SSHで入り、そのフォルダで bash setup-wpcli.sh を実行する。 - タイムゾーン、パーマリンク、カテゴリー4つ、固定ページ3つ（下書き）、プラグイン（SEO SIMPLE PACK・WP Multibyte Patch・Contact Form 7・Pochipp・miagetabi-core）が、まとめて設定される。 - 何度実行しても、同じものが二重にできることはない。

ステップ5　Googleにつなぐ（20分）

  1. Search Console：「URLプレフィックス」で https://ドメイン/ を登録し、HTMLタグの確認コードを SEO SIMPLE PACK に貼る。
  2. Search Console → サイトマップ に wp-sitemap.xml を送信する（WordPressが自動で作るもの）。
  3. GA4：プロパティを作り、測定IDを SEO SIMPLE PACK に貼る。
  4. X・Instagram のプロフィールにサイトのURLを入れる。

延期が発表されたとき（30分以内）

  1. 投稿の「今の状況」を 延期 か 日程変更 にする（構造化データの eventStatus も自動で変わる）。
  2. 新しい日が出たら「イベント日」を直す。
  3. 「最終確認を『いま』にする」→ 更新。
  4. 本文の「更新履歴」に1行足す → Xで告知（管理アプリの「SNS」タブ）。

投稿一覧に「イベント日（T−5 など）・状況・最終確認」の列が出るので、直前の記事を見落とさない。
