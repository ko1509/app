## 2-2. カテゴリ構成とURL設計

方針：
- 3本柱を**最上位ディレクトリ**にする（`/launch/` `/sky/` `/ride/`）。分析・収益の比較がしやすく、将来のB2B営業で「宇宙観光」「モビリティ観光」を切り出しやすい。
- **「常設ガイド」と「回ごとの記事」を分ける**。常設ガイド（射場・撮り方・地域）は長く評価を積み、回ごとの記事は直前に検索される。回ごとの記事から常設ガイドへ内部リンクで評価を集める。
- URLは英小文字・ハイフン。年月を入れるのは「回ごとの記事」だけにする。

```
/                                   トップ（直近30日のイベント一覧＝カレンダーの簡易版）
├─ /calendar/                       観覧カレンダー（フェーズ2でツール化）
│
├─ /launch/                         ロケット打ち上げ
│   ├─ /launch/spot/tanegashima/    【常設】種子島で見る完全ガイド
│   ├─ /launch/spot/uchinoura/      【常設】内之浦
│   ├─ /launch/spot/kii/            【常設】串本（スペースポート紀伊）
│   ├─ /launch/spot/taiki/          【常設】北海道大樹町
│   ├─ /launch/guide/first-time/    【常設】初めての打ち上げ観覧（延期・持ち物の総論）
│   ├─ /launch/guide/delay/         【常設】延期になったときの動き方
│   └─ /launch/2026-12-h3-f8/       【回ごと】年-月-機体-号機
│
├─ /sky/                            天体イベント
│   ├─ /sky/howto/smartphone/       【常設】スマホで星を撮る基本
│   ├─ /sky/howto/meteor/           【常設】流星群の見方・撮り方
│   ├─ /sky/howto/iss/              【常設】ISS・人工衛星の見つけ方
│   ├─ /sky/place/                  【常設】地方別 星がきれいに見える場所
│   └─ /sky/2026-12-geminids/       【回ごと】年-月-イベント名
│
├─ /ride/                           自動運転バス・ロボタクシー
│   ├─ /ride/list/                  【常設】全国一覧（誰でも乗れる順）※最重要ハブ
│   ├─ /ride/area/kanto/            【常設】地方別まとめ
│   ├─ /ride/guide/level/           【常設】「レベル4」って何？を一言で
│   └─ /ride/ibaraki-sakai/         【路線ごと】都道府県-地名（+事業者）
│
├─ /gear/                           機材・持ち物（アフィリエイトの受け皿）
│   ├─ /gear/smartphone-tripod/
│   └─ /gear/binoculars/
│
├─ /for-business/                   自治体・観光協会向け（フェーズ3）
└─ /about/ /policy/ /contact/       運営者情報・広告ポリシー・お問い合わせ
```

**タグ（横串）**：地域（`/tag/kagoshima/`）、季節、無料、日帰り、子連れOK。トップとカレンダーは「日付順」で横串に並べる。

**構造化データ**：回ごとの記事には `Event` スキーマ（startDate, location, eventStatus = EventScheduled / EventPostponed / EventRescheduled）を入れる。延期時は `eventStatus` も更新する（検索結果に反映されやすい）。

**CMS**：WordPress（テーマはSWELL等）か、Astro＋Markdown（AIで下書きしたMarkdownをそのまま入れられる）。細切れの時間で作業するなら**Markdown＋Git管理**だとAIとの相性が良い。フロントマターに `last_verified` を持たせ、冒頭に自動表示する。

## 2-3. 「直前に検索が集中する」性質を活かした更新ルール

検索は「イベント当日〜3日前」に一気に増え、終わると急に減る（推測：Googleトレンドで「ふたご座流星群」「H3 打ち上げ」を見るとこの形。公開後に自分のSearch Consoleで確かめる）。だから**公開は早く、更新は直前に厚く**する。

### ルール1：公開は早めに（「T-○日」で管理）

| 種類 | 初回公開 | 理由 |
|---|---|---|
| 流星群・月食などの天体イベント | **T-30日** | 日付が確定しているため早く書ける。評価が付くまでの時間を稼ぐ |
| ロケット打ち上げ（日付発表後） | **発表から48時間以内** | 発表直後に検索が始まる。速さで勝つ |
| ロケット打ち上げ（日付未発表） | 「○年度打ち上げ予定」として常設ガイド内に節を作る | 発表後に回ごとの記事を切り出す |
| 自動運転（期間限定の運行） | **運行開始T-14日** or 発表から72時間以内 | 予約枠が埋まる前に |
| 自動運転（定期運行） | 随時（常設） | 乗車レポートを足していく |

### ルール2：直前は更新を厚くする（更新の頻度）

| タイミング | やること |
|---|---|
| T-7日 | 天気の傾向・宿の空き状況・交通の注意を追記。SNSで告知①（下の90日計画を参照） |
| T-3日 | 公式情報を再確認。タイトルに曜日を入れる（例：「今夜」「14日(月)」） |
| T-1日 | 天気予報を反映。延期情報があれば即時更新。SNS告知② |
| **当日** | 冒頭ボックスの「今の状況」を更新（打ち上げは**公式発表から30分以内**を目標）。ライブ中継リンクを上に |
| T+1日 | 結果を追記（打ち上げ成功・見え方の報告・自分の写真）。「次のチャンス」への導線を冒頭へ |
| T+7日 | タイトルを「振り返り＋次回予告」に寄せる or 次回記事へ301（年1回の天体イベントは翌年用に記事を使い回すか判断） |

### ルール3：延期への対応（ロケット特有）

- 延期が発表されたら：①冒頭の状況ラベルを「延期」に ②新しい日時（未定なら「未定」） ③更新時刻 ④`Event` スキーマの `eventStatus` を更新 ⑤Xで告知（「延期になりました。宿のキャンセル・延長の考え方はこちら」）
- 延期が続く打ち上げほど検索が長く続くので、**延期の歴史（いつ・なぜ延期されたか）を時系列でまとめる**節を付けると他サイトとの差になる。

### ルール4：毎年くり返すイベントは「同じURLを毎年更新」

- 流星群は `/sky/geminids/`（年なし）を毎年更新する方法と、`/sky/2026-12-geminids/` の年ごと記事にする方法がある。**おすすめは年なしURLを毎年更新**（評価を積み上げられる）。年ごとの細かい記録は記事内の「過去の観測記録」に追記する。上のURL設計の年入りURLは、1回限りのイベント（月食・彗星・特定の打ち上げ）にだけ使う。

### ルール5：確認日時の表示を義務にする

- すべての記事の冒頭に「最終確認：YYYY-MM-DD HH:MM（出典：○○）」を出す。
- 事実が変わりやすいもの（運行時刻・打ち上げ日時）は公式URLを**2つ以上**付ける。
- 推測には必ず「推測」ラベル。

### ルール6：AIでの下書き作業を定型化する

1. **リサーチ用プロンプト**（イベント名＋公式URLを入力 → 日時・場所・出典の表を出させる）
2. **構成用プロンプト**（テンプレートA/B/C＋表 → 見出しと本文の下書き）
3. **事実確認（人がやる）**：日時・料金・予約の要否だけは必ず公式ページで目視確認。AIの出力をそのまま公開しない
4. **更新用プロンプト**（公式の新しい発表文を貼る → 差分だけ書き換えた案と「更新履歴」の1行を出させる）

詳しいプロンプト例は `05-ai-workflow.md` に。
