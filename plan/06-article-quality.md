# 6. 記事の品質設計（エージェントに書かせる前に決めること）

作成日：2026-10-15。KOAlil.com の作成・査読の仕組みを参考に、ミアゲタビの題材に合わせて考え直したもの。エージェントの手順書（`app/ops/article-manual.md`・`app/ops/review-manual.md`）は、この設計から作る。

---

## 6-1. ミアゲタビの記事は「何をする記事」か

**読んだ人が、その日・その時刻・その場所で、迷わず動けるようにする記事。**

ふつうの解説記事と違い、読者はこのあと実際に動く（夜中に起きる、島へ飛ぶ、寒い場所で待つ）。だから誤りの損失が大きい。

| 誤りの種類 | 読者の損失 | 例 |
|---|---|---|
| 時刻・日付の誤り | 見逃す | 世界時を日本時間に直し忘れる。「15日未明」を15日の夜と書く。曜日の取り違え |
| 状況の古さ | 無駄足・宿代 | 延期が発表されたのに「予定どおり」のまま |
| 見え方の誇張 | がっかり・信頼を失う | 「1時間に100個」（暗い空の理論値）を街中でも見えるように書く。日本で見えない日食を見えるように書く |
| 場所の誤り | 入れない・危ない | 立入禁止区域や私有地を見学場として紹介する。駐車場がない場所に車で行かせる |
| 安全の抜け | けが・事故 | 日食を直接見る。夜道・寒さ・交通規制 |

→ **品質の第一は「時刻・場所・状況が正しく、確かめた日時が書いてあること」。** 文章のうまさは二の次。

## 6-2. 質を決める8つの柱

### 柱1　時刻の正しさ（このサイトでいちばん大事）
- 時刻は**日本時間（JST）だけ**で書く。世界時（UT）の資料（NASA・IMOなど）は、**コードで変換**してから使う。暗算しない。
- **曜日はコードで出す**（`python3 -c "import datetime; ..."`）。曜日の書き間違いは信頼を一番落とす。
- 「未明」「深夜」は日付があいまいになる。**「14日（月）の夜から15日（火）の明け方」**のように、夜をまたぐ時間帯は2つの日付で書く。
- 打ち上げは「打ち上げ予定時刻」「打ち上げ時間帯（ウィンドウ）」「予備期間」を分けて書く。
- 本文に相対日付（「今週末」「来月」「今年の」）を書かない。タイトルに入れる「今夜」「明日」は直前更新のときだけ。

### 柱2　一次情報と確認日時
- 根拠の優先順位：
  1. 当事者：JAXA、スペースワン、インターステラテクノロジズ、各施設
  2. 自治体：南種子町、肝付町、串本町、大樹町、鹿児島県など
  3. 国立天文台（ほしぞら情報・暦計算室）
  4. NASA、IMO（国際流星機構）
  5. 報道
  6. その他（まとめサイト・個人ブログは根拠にしない）
- 記事の冒頭に**「最終確認：YYYY年M月D日 H:MM」**を出す（プラグインの最終確認欄）。打ち上げの記事は、書いた時点でもう一度公式の状況を確かめる。
- **確かめられない数字・事実は書かない。** 「要確認」と添えて書くのも不可（KOAlil と同じ決まり）。
- 例外として「**編集部の目安**」は書いてよい。ただし、確かめた事実から導いた理由を必ず添える。
  - 例：「交通規制が3時から始まると町が発表しているので、2時までに着くのが目安です」

### 柱3　「どう見えるか」を具体的に（情報利得の中心）
ほかのサイトにない価値は、**読者の場所から何がどう見えるか**を具体的に言えること。
- 天体：主な都市（札幌・東京・大阪・福岡・那覇）での**方角と高さ（地平線から何度）**を、見ごろの時刻について**コードで計算**し、国立天文台の記述と食い違わないか確かめる（計算の道具は `ops/sky.py`）。
- 月明かり：月の出・月の入り・月齢をコードで出し、「何時から何時は月がなく暗い」と書く。
- 見える数：「暗い空での目安」と「街明かりのある場所の目安」を分ける。出典のある数字だけを使い、街中の数に出典がなければ書かない（「街中ではかなり減ります」と言うにとどめる）。
- 打ち上げ：見学場ごとに「射点（発射台）から何km」「射点が見えるか（山に隠れるか）」「ロケットが飛ぶ方向」を書く。遠くの都市から見えるかは、公式の案内か過去の実績（報道・公式の写真）があるときだけ書く。

### 柱4　動くための情報（ロジスティクス）
各記事に、少なくとも次のうち該当するものを入れる。
- 当日のタイムライン（何時に出て、何時に着き、何時に始まり、何時に帰れるか）
- 交通（便の時刻・本数、レンタカーの台数、規制）と宿（埋まりやすさ）
- 延期・中止・曇りのときの動き方（予備日をどう押さえるか、どこで情報が出るか）
- 持ち物（季節と時刻に合わせる）
- 天気の確かめ方（どのサイトの何を見るか）

### 柱5　初めての人に読める文章
- 中学生が読んでわかる言葉で書く。専門用語は使わないか、出てきた最初の1回だけ一言で言い換える。
  - 極大 → いちばん多く流れる時間帯
  - 放射点 → 流れ星が飛び出してくるように見える点
  - 射点 → 発射台
  - 衝 → 一晩中見える時期
  - 等級 → 明るさ（小さいほど明るい）
- **各見出しの最初の1〜2文で答える**（アンサーファースト）。理由や背景はそのあと。
- 1文はおおむね40字以内。二重否定を使わない。
- 表は**3列まで**、セルは短く（スマホで読める幅）。説明は表の外に書く。
- 「美しい天体ショー」「一生に一度」「圧巻」のような中身のない飾りを書かない。

### 柱6　体験の誠実さ
- 行っていない・見ていないのに、行った・見たように書かない（**体験の偽装は公開を止める誤り**）。
- 運営者の体験が入る記事だけ、体験記入欄 `[体験記入: 何を書くか]` を置く（依頼で「体験を入れる」を選んだときだけ）。
- 写真は、運営者が撮ったものか、利用規約で使える公式の画像だけ。**AIで作った画像を実際の写真のように使わない**（図・イラストは「図」と明記する）。

### 柱7　安全と配慮
- 日食：太陽を直接見ない・日食グラスの注意を冒頭に（この期間は日本で見える日食はないが、海外遠征の記事では必須）。
- 夜：私有地・立入禁止区域に入らない。暗い道・寒さ・車の運転・駐車マナー。
- 打ち上げ：射点の周り3kmは当日立入禁止（JAXA）。交通規制に従う。ドローンを飛ばさない。
- **エネルギー・原子力の話題は扱わない**（サイトの決まり）。

### 柱8　収益化の節度
- アフィリエイトは、読者がその場面で本当に必要なもの（宿・交通・三脚・防寒）だけ。記事の流れの中で、必要な理由と一緒に置く。
- 値段・在庫・ポイントを本文に書かない（変わるため）。広告を含む記事はPR表記。
- 「今すぐ予約しないと売り切れ」のような煽りを書かない。

## 6-3. どの記事にも入れる「ミアゲタビならではの要素」

記事ごとに、次のうち**2つ以上**を入れる（査読で確かめる）。
1. 計算した方角・高さ・時刻（複数の都市）
2. 当日のタイムライン
3. 延期・曇りのときの動き方
4. 見学場・観察場所の比較表
5. スマホの具体的な設定（機種別）
6. 過去の実績（前回の延期の経緯・混雑の報道など。出典つき）

## 6-4. AIが書くときに起きやすい失敗（査読で必ず見る）

| 失敗 | 防ぎ方 |
|---|---|
| 世界時のまま書く／変換を間違える | コードで変換。出典の時刻系（UT・JST）を報告に書く |
| 曜日の誤り | コードで出す |
| 「毎年○日」と決めつける | その年の公式ページで確かめる |
| ZHR（理論値）を実際に見える数として書く | 「暗い空での目安」と明記。出典の数字だけ |
| 見えない現象を「見える」と書く（日本で見えない日食、半影月食） | 国立天文台・NASAで日本からの見え方を確かめる |
| 見学場・駐車場・トイレの捏造 | 自治体・JAXAの案内にあるものだけ |
| H3とH-IIA、号機・ミッション名の取り違え | JAXAの特設ページで照合 |
| 延期後の古い日時が残る | 書いた時点で公式の状況を再確認。冒頭の状況欄を必ず埋める |
| 旅行の決まり文句（「絶景」「一生に一度」） | 柱5のとおり削る |
| 根拠のない一般化（「多くの人が」「いつも混む」） | 出典があるときだけ。なければ確かめ方を書く |

## 6-5. 作成と査読の流れ

```
記事ボードの「エージェントに書かせる」
   ↓（依頼：jobs に kind "article"）
記事作成エージェント … 一次情報を開いて確かめる → 計算する → 書く → 自己査読
   ↓（依頼：kind "review"）
査読エージェント（別のセッション） … 主張を全部抜き出して一次情報で確かめ直す → A〜D で判定
   ├─ A なら：記事は「確認待ち」へ。運営者が目で見て WordPress に貼る
   └─ B 以下：指摘（直した文の案つき）を作成エージェントに返す（最大3回）
        ほかの記事にも効く指摘は「教訓」として作成エージェントに残す
```

- **合格は A だけ**（P0・P1がゼロ）。
- 査読は、作成とは**別のセッション・別の手順書**で行う（同じ思い込みを避ける）。
- 公開は運営者が行う。サーバーが海外からのREST APIの利用を止めているため、エージェントはWordPressに書き込まない（入稿の自動化は、運営者が設定を変えたあとで検討する）。

### 判定の基準

| 区分 | 意味 | 例 |
|---|---|---|
| P0：公開を止める | 時刻・日付・場所・状況の誤り、見え方の誇張、体験の偽装、安全の抜け、捏造したリンク・数字 | 世界時のまま、延期前の日時、日本で見えないのに見えると書く |
| P1：公開前に直す | 一次情報で確かめていない数字、検索意図に答えていない見出し、ならではの要素が2つ未満、専門用語の説明なし、主要な数字に根拠のリンクがない | 「1時間に60個」に出典がない |
| P2：改善 | 読みやすさ、表の形、言い回し、写真の案 | 1文が長い、表が4列 |

総合：A（P0・P1なし）／B（P1あり）／C（P0あり）／D（構成から作り直し）。

## 6-6. エージェントが出すもの（1本の記事あたり）

| 項目 | 中身 | 使い道 |
|---|---|---|
| 本文（Markdown） | タイトル・導入・見出し・本文・FAQ・確認日の一文 | 運営者が読む |
| WordPress用ブロック | 本文を Gutenberg のブロックに変換したもの | 編集画面の「コードエディター」に貼るだけで、SWELLの見出し・表・リストになる |
| イベント情報欄の値 | イベント日・時刻・状況・場所・公式URL・メモ | プラグインの入力欄に写す |
| タイトル案・メタディスクリプション | タイトル（32字前後）と説明文（80〜120字） | SEO SIMPLE PACK に入れる |
| 更新チェックリスト | T−7・T−3・T−1・当日に何を確かめ直すか | 管理アプリの更新タスクに使う |
| 報告 | 確かめた出典（URL・確認日時・何を確かめたか）、計算した値、判断の分かれ目 | 査読エージェントが照合する |

## 6-7. 次の段階（品質を保ったまま広げる）

1. **延期ウォッチ**：JAXA・スペースワン・インターステラの「お知らせ」を毎日見て、打ち上げ日の変更を管理アプリのイベントに反映し、該当記事の更新を依頼する（延期の多い題材なので効果が大きい）。
2. **アイデア**：国立天文台の月ごとの「ほしぞら情報」と打ち上げ予定から、次に書く記事を提案する。
3. **SNSの下書き**：査読に合格した記事から、X・Instagram の告知文を作る。
4. **入稿**：WordPress のアプリケーションパスワードを用意し、サーバーの海外アクセス制限を調整したあとで検討する。
