## 1. サイトの基本

### 目的・読者・ジャンル・地域

運営マニュアル（原文）：

> サイトの目的：ロケットの打ち上げ、天体イベント、宇宙スポットを、初めての人でも「いつ・どこへ・何を持って」行けばいいかわかるように案内する。
> 読者：宇宙に興味はあるが詳しくない人。現地に行く人と、家の近くの空や中継で見る人の両方。

- 補足（手順書 `site-rules.md`）：「中学生が読んでわかる言葉で書く」。初めて打ち上げを見に行く人、子どもと流星群を見たい家族を想定。「『知って終わり』ではなく『見に行ける』記事だけを書く。」
- 扱う（運営マニュアル原文）：「国内のロケット打ち上げ観覧（種子島・内之浦・紀伊・大樹）／日本から見える天体イベント／見学できる宇宙施設と星空スポット／見に行くための持ち物・宿・交通」
- 条件つき：「海外の打ち上げや日食：日本から見に行く人がいるもの、中継で見られるものだけ。宇宙ニュース：『見られる』『行ける』につながるときだけ（ニュース速報のサイトにはならない）」
- 扱わない：「宇宙ビジネス・投資の話、政治的な論評、エネルギー・原子力の話題、UFO・占星術などの疑似科学、事故をあおる記事」
- 地域：国内中心。時刻は日本時間のみ。主な射場は種子島（南種子町）・内之浦（肝付町）・串本（スペースポート紀伊）・大樹町。
- カテゴリ（スラッグ）：打ち上げを見る `launch`／星空を見る `sky`／宇宙を訪ねる `spot`／機材・持ち物 `gear`／お知らせ `news`（エージェントは書かない）。新しいカテゴリ・子カテゴリは作らない。
- 守る3つの約束（トップページにも掲載）：
  1. 「日時・場所・料金は、公式の発表を見てから書く。確かめられないことは『推測』と書く。」
  2. 「すべての記事に『最終確認日時』を出す。」
  3. 「延期などの変更は、発表から30分以内の更新を目指す。」

### 他サイトとの違い・収益モデル

- 差別化（原文：記事にするかの「3つの問い」。3つとも Yes のときだけ書く）：
  1. 「読者が『見る』『見に行く』ために使えるか。」
  2. 「公式の一次情報で確かめられるか。」
  3. 「ほかのサイトにない要素（計算した方角や時刻、当日のタイムライン、延期のときの動き方、見学場の比較など）を2つ以上入れられるか。」
  - 「1つでも No なら、常設ガイドの中の一節にするか、書かない。」
- トーン：下記 2 章。
- 収益モデル：アフィリエイト（宿・交通・三脚・防寒具・双眼鏡など。`gear` カテゴリが「アフィリエイトの中心」）。詳細と現状は 7 章。**現時点で収益が出ているか、どの ASP に実際に参加済みかは不明**（7章）。アクセス解析はあるが、収益の数字は db にありません。
- 技術構成（運営マニュアルより）：ConoHa WING（契約満了 2027-02-01）／WordPress 7.1.3／テーマ SWELL 2.19.0＋子テーマ／SEO SIMPLE PACK／Pochipp／GA4。2026-10-24 にサイト全体を「夜空の雑誌」風の新デザインに作り直した（デザインはカスタマイザーの追加 CSS・フッターのコードで実装）。

## 2. 言語・文体

- 言語：記事本文・SNS 本文とも**日本語のみ**。運営者との連絡も日本語。英語は、アイキャッチの小さな一文（`en`）と、英字の小見出し・ラベルだけ。
- **一人称：明文のルールは見つかりません（不明）。** 実際の稿は「編集部の計算」「編集部の目安」「このページは…まとめました」のように、「編集部」「このページ」を使い、「私」「当サイト」は使っていません（a22 の稿で確認）。「編集部の目安」は「確かめた事実から導いた理由と一緒にだけ書く」（`site-rules.md` 3）。
- トーン（運営マニュアル原文）：
  > 落ち着いた案内役として書く。あおらない、盛らない。「絶景」「一生に一度」「圧巻」は使わない。
  > 見え方は正直に。「暗い空での目安」と「街中での見え方」を分け、見えにくいときは最初にそう書く。
  > 結論を先に書く。各見出しの最初の1〜2文で答える。
  > 読者を急かさない。「今すぐ予約しないと売り切れ」のような書き方はしない。
- 避ける表現（手順書での範囲）：「絶景」「一生に一度」「圧巻」「最強」「必見」（SNS は加えて「見逃し厳禁」）。読者を急かす言い方。見え方を盛る書き方。「多くの人が」「いつも混む」のような根拠のない一般化。値段・在庫・ポイント。
- 文のつくり：1文は短く。専門用語は最初の1回だけ言い換える（例：「フェアリング＝衛星を包む先端のカバー」「極大＝いちばん多く流れる時間帯」「放射点＝流れ星が飛び出してくるように見える点」「等級＝明るさの目盛り〈小さいほど明るい〉」）。1段落は3〜4行まで、太字は1段落に1か所まで、表は3列まで（セルは短く、目安15字）。
- 公式の文面が「ご遠慮ください」「お願いします」のときは、「禁止」と強めずにそのまま写す（教訓11）。
- 同じページに同じ数字を2回書かない（直すときに片方が古くなる）。要点ボックスの数字は本文では言い換える。
- **表記ルール（運営マニュアル・`site-rules.md` の表。原文）**

| 項目 | 書き方 | 書かない例 |
|---|---|---|
| 日付 | 10月20日（火）。年がまたがるときは2026年10月20日（火） | 10/20、20日（火曜日） |
| 時刻 | 24時間制で4時41分。表と要点ボックスは4:41 | 午前4時41分、AM4:41 |
| 夜をまたぐ時間 | 14日（月）の夜から15日（火）の明け方 | 15日未明 |
| 時刻の基準 | 日本時間だけ。JST は英字ラベルの中だけ | 世界時（UT）のまま |
| 数字 | 半角。4けた以上はカンマ（2,000人） | 全角の数字 |
| ロケット名 | H3ロケット10号機。2回目からはH3 10号機 | H3-10、H-3 |
| 打ち上げ | 「打ち上げ」で統一。公式名に「打上げ」とあるときだけそのまま | 発射（射点・発射台は可） |
| 方角 | 南東の空、高さ30度くらい | 右のほう、上のほう |
| 施設名 | 1回目は正式名。2回目から略してよい | いきなり略称 |

- 通貨・料金：**値段・在庫・ポイントは書かない**（機材記事・SNS とも。「値段は書かない。使っていない物を『使ってみた』と書かない。」）。公式の料金（入場料・宿泊料金など）をどう書くかの独立した表記ルールは見つかりません（不明）。公式の値を出典つきで書く、が実際の運用です。
- 年度：「年度内」とだけ書かず「2026年度内」のように年を入れる（教訓13）。
- 相対日付（今週末・来月・昨日・先週・今年の）は記事にも db にも書かない（`agent-jobs.md` 3、査読 P1）。ただし「今夜」「明日」は前日と当日だけ使い、過ぎたら外す。
- タイトル：32字前後。検索される言葉（イベント名・号機・場所）を前に、記事が答える問い（いつ・どこで・何時）を入れる。例（運営マニュアル）：「H3ロケット10号機はいつ？ 種子島で見る場所と時間」。曜日は3日前の更新から入れる。毎年くり返すイベントは、タイトルに年を入れて毎年書き換える（URL には入れない）。
- 説明文（メタディスクリプション）：80〜120字。誰に向けた記事か、何がわかるか、最終確認日を入れる。
- URL：英小文字とハイフン、2階層まで。毎年くり返すイベントは年なし（`/sky/geminids/`）、1回きりの打ち上げは号機入り（`/launch/h3-f10-mmx/`）。パーマリンクは変えない。

## 3. 事実と体験の扱い

### 事実・数値・料金・制度の確認方法と、根拠として認める情報源

運営マニュアル・手順書（原文）：

> 根拠の順番：当事者（JAXA・スペースワン・インターステラテクノロジズ・各施設）→ 自治体 → 国立天文台 → NASA・IMO → 報道。まとめサイト、個人ブログ、SNSのうわさは根拠にしない。
> 時刻は日本時間だけで書く。世界時からの変換と曜日は、暗算せずコードで出す。

- 確かめ方（`article-manual.md` 4-2）：ページは**実際に開いて読む**（検索結果の抜粋だけで書かない。WebFetch が失敗したら `curl -sL`）。数字・日付・時刻・場所・料金・定員・予約方法は、すべて出典ページで確かめる。「その年の情報で確かめる。『毎年○日』『例年』は過去の年の掲載も確かめたときだけ。」資料が食い違うときは当事者の値を使い、食い違いを本文と `report` に書く。
- 認める情報源の実URL（`article-manual.md` 4-1）：JAXA（特設ページ fanfun.jaxa.jp/countdown/、プレス jaxa.jp/press/）、スペースワン、インターステラテクノロジズ、各施設公式／南種子町・肝付町・串本町・和歌山県（wakayama-rocket.com）・鹿児島県／国立天文台（ほしぞら情報 nao.ac.jp/astro/sky/、暦計算室 eco.mtk.nao.ac.jp/koyomi/）／IMO（流星群カレンダー）・NASA（日食）・「#きぼうを見よう」／報道は日付つきで過去の混雑・延期の経緯などに。
- 計算は暗算せず `sky.py`（曜日・世界時→日本時間・月の出入り・月齢・流星群の放射点・惑星の方角と高さ）。**日の出・日の入りは `sky.py` ではなく国立天文台 暦計算室（東京）の値を使う**（`sky.py` は標高40m設定で3〜4分ずれる。教訓6）。方角は16方位で1つ、高さは±5°までのずれを許容、超えると P0（方角・時刻）／P1（高さ）。
- 公式と報道が食い違うとき：「公式のほうを書き、食い違いがあることにも触れる。」
- 打ち上げ・公開・運行の「今の状況」は、書いているとき・査読しているときに、それぞれ公式ページで確かめ直す。
- AI の使い方（運営マニュアル原文）：「AIの下書きをそのまま公開しない。日時・場所・料金・予約の要否は、必ず人が公式ページを開いて目で確かめる。」「AIは下書き・計算・調べものの手伝い。事実が正しいか、公開するかどうかは人が決める。」「AIを使っていることは隠さない。運営者情報ページに使い方を書く。」
  - **現状との食い違い（要注意）**：現在のアプリは、査読 A → アイキャッチ → 入稿が**自動**で WordPress に公開する設計です（運営者の「このサイトはクロードで自動運転が基本設計です」という指示による）。運営マニュアルの「公開は必ず運営者」と食い違っています。運営者の最終確認の工程を AI HUB でどう扱うかは**未決定**です。

### 実体験の記述ルール

- 原文（運営マニュアル）：「行っていない・見ていないことを、体験したように書かない。体験談は運営者が実際に行ったときだけ、その日付を添えて書く。」
- 誰が体験した前提か：**運営者が実際に行った場合だけ**。記事の依頼の `withExperience` が `true` のときだけ、運営者が書き込む欄 `[体験記入: 何を書いてほしいか]`（1記事3か所まで）を置く。`false` なら置かない。
- 体験がない場合：スポット記事は公式情報だけで書き、「訪問レポートは準備中」と明記する。機材記事は「使っていない物を『使ってみた』と書かない」。
- 体験の偽装（「実際に行ってみると」「スタッフによると」など）は P0（公開を止める）。
- 写真：運営者が撮ったものか、利用規約で使える公式画像だけ。AI の写真風画像は使わない。図には「模式図」「簡略化」と書く。エージェントは写真を入れず、`report` の「写真の案」に被写体を書くだけ。

### 根拠がない・古い可能性がある情報の扱い

- 「確かめられないことは書かない。どうしても必要な見込みだけ『推測』と書き、理由を添える。」例（原文）：「推測：前回の10号機では満車が5時ごろだったため（南種子町の発表）」。「『要確認』と書いて残すのは不可。」
- 「推測」と書いたら、理由に挙げた数字だけで足し算・引き算をして、結論が出るかを確かめる。出なければ結論を弱める（教訓16）。
- 「まだ起きていないこと（延期など）を『〜でした』と過去形で書かない」（教訓17）。
- 入稿のとき、稿の「最終確認」が7日より前、または `eventDate` が今日より前なら、「事実が古い可能性がある」として、入稿後に直しの案（`update` 依頼）を自動で積む（`publish-manual.md` 3 手順4）。
- 点検（audit）が、毎朝、公開済み記事の「最終確認」の古さを見る：イベントが7日以内で最終確認が3日以上前、イベント終了2日後に「予定どおり」のまま、常設ガイドで90日以上前、のいずれかを拾う。

## 4. 記事の作り方（工程順）

全体の流れ（自動運転の形。`agent-jobs.md`）：

```
企画(planner) → 記事選定(selector) → 作成(writer) ⇄ 査読(reviewer) → 画像(designer) → 入稿(publisher) → 公開済み
                                                          公式ウォッチ/点検/受信箱担当 → 直し(update)・差し替え
```

記事カードの状態：`企画中 → 執筆中（旧名「下書き」）→ 査読中 →（差し戻しで執筆中へ）→ 公開待ち → 公開済み → 要更新`。査定で落ちたものは `保留`、運営者が見送ったものは `見送り`。

### 4-1 企画（planner／selector。`planner-manual.md`・`selector-manual.md`）

- **入力**：`articles` 全件・`events` 全件・`settings/plannerLog`（見送り理由）・カードの `assess`・受信箱の `planReview`/`idea`・公式の予定（国立天文台、JAXA、スペースワン、インターステラ、IMO）。
- **やること**：
  - 定時は月・木の朝7時台（企画）。`企画中` が20件以上あれば出さない（「企画が20件あるため出しません」）。
  - 候補は期限順：①打ち上げの日時が発表され記事が無いもの（発表から48時間以内）②30〜60日後の天体イベントで記事が無いもの③足りない常設ガイド④運営者のメモのテーマ。
  - 「3つの問い」で絞る。1つでも No なら出さない。扱わない話題（ビジネス・投資・エネルギー・原子力・疑似科学・事故をあおる）は出さない。
  - 配分：直近6件で同じカテゴリが3件以上なら他を優先。`gear` は、その機材が自然に要る記事が公開済みのときだけ。
  - 重複を除く（保留・見送りを含む既存カード・見送られた企画と同じ題材は出さない。毎年のイベントは既存カードの年を更新する提案にする）。
  - 1回に5件まで。
- **出力（カードの書式・原文）**：

```json

 "tags": ["決まった一覧のものだけ"], "path": "/sky/leonids/（ops/site-rules.md の 4 の URL の決まり）",
 "template": "A 打ち上げ|B 天体|C 宇宙スポット|常設", "keyword": "検索キーワード", "intent": "検索意図（読者が知りたいこと）",
 "eventDate": "YYYY-MM-DD または空", "publishBy": "YYYY-MM-DD（期限の決まりから計算）または空",
 "monetize": "アフィリエイトの導線（宿・交通・三脚・防寒など。無ければ「なし」）",

          "unique": ["ミアゲタビならではの要素（2つ以上）"], "questions3": ["…","…","…"],
```

  - `publishBy`：天体＝イベントの30日前、打ち上げ＝発表から48時間後、それ以外は空。
- **却下の基準（記事選定の査定。100点満点）**：3つの問い30／一次情報15／検索意図15／重なり15／期限15（`publishBy` まで書いて査読を通す日数7日があるか）／決まり10。「70点以上で、0点の観点が無ければ合格（OK）」。扱わない話題・既存カードと同題材・期限切れは点にかかわらず不合格。不合格は `保留` にして受信箱 `planReview` に理由を書く。**不合格の例（実物）**：a12「首都圏から行ける星空がきれいな場所」＝62点。「3つの問い(18/30)：行き先の候補地が決まっておらず、公式の一次情報で答えられるか判断できない」「一次情報(5/15)：根拠にする自治体・観光協会・施設の公式ページが特定できない」「検索意図(11/15)：範囲が広い」。→運営者が「見送り」にした。

- **完了条件**：カードが `企画中`（優先度つき）で存在する／査定で OK が付いて `執筆中` に回る。

### 4-2 執筆（writer。`article-manual.md`）

- **入力**：`jobs/<ID>`・`articles/<ID>`・題材の `events`（値は古いことがあるので信じない）・公開済みカード（内部リンク用）・`settings/writerLessons`（査読が足した教訓。手順書の追補として守る）・書き直しなら `review.text` と `reviewHistory`。
- **やること**：構成（検索意図を3〜6個の具体的な問いに分け、型の見出しに割り当てる）→調べる→計算→書く→図を2つ以上作る→Markdown を `md2blocks.py` で WordPress ブロックに変換→自己点検→保存→査読に回す。運営者に聞かないと書けないこと（体験の有無、方針の判断）は推測で埋めず受信箱に質問を出す。
- **記事の構成テンプレート（`site-rules.md` 5。原文）**
  - 打ち上げ観覧：「要点ボックス（今の状況・日時・場所・予備期間・見る方法の要点）→ 最終確認 → 導入2〜3文 → `## まず結論`（読者のタイプ別におすすめの見方を3つまで）→ 基本情報 → 見る場所 → 当日の動き方 → 行き方 → 延期のとき → よくある質問 → 出典 → 更新履歴」
  - 天体イベント：「要点ボックス（いつ〈夜をまたぐときは2つの日付〉・方角と高さ・どのくらい見えるか〈暗い空の目安と街中を分ける〉・月明かり・天気の確認先）→ 最終確認 → 導入 → `## まず結論`（今年の見やすさを1段落で）→ 時刻表 → 主な都市での方角と高さ → 場所選び → スマホでの撮り方 → 持ち物と寒さ対策 → 曇ったとき・見逃したとき → よくある質問 → 出典 → 更新履歴」
  - 宇宙スポット：「要点ボックス（どこ〈都道府県・最寄り駅〉・予約が要るか・料金・何時間あれば楽しめるか）→ 最終確認 → どんな場所か → 見どころ（3つまで）→ 予約と当日の流れ → 訪問レポート → 行き方 → あわせて行きたい場所 → 休館・変更の確かめ方 → よくある質問 → 出典 → 更新履歴」

- **部品（Markdown の `:::`。`md2blocks.py` がブロックに変換）**：`:::info 英字の見出し`（要点ボックス。記事の冒頭に1つだけ。「今の状況」の値の頭に `[go]` `[delay]` `[stop]` `[sky]` `[open]` `[done]`）／`最終確認：YYYY-MM-DD H:MM（出典：〇〇）`（要点ボックスの直後）／`:::point`（注意・安全。1記事2つまで）／`:::fig FIG.01 キャプション` ＋ `@figures/名前.svg`（図。1記事2つ以上〔機材記事は1つ〕。キャプションに「模式図」か「sky.py で計算」と出典）／`:::src`（出典。公式を先に。記事の最後）／`:::history`（更新履歴）。よくある質問は `## よくある質問` の下に `### 質問` と答え（3〜4組）。
- **稿の先頭（frontmatter。原文）**：`title`（32字前後）・`description`（80〜120字）・`slug`・`category`・`tags`（決まった表のものだけ）。
- **見出しの付け方**：短く、見出しだけで中身が分かる形。各 H2 の最初の1〜2文が答え。1つの見出しの下は2〜3段落まで。検索意図（`intent`・`keyword`）に直接答える見出しを必ず入れる。

- **必須要素**：要点ボックス（3〜6項目）、最終確認の一行、「まず結論」、ミアゲタビならではの要素を2つ以上（計算した方角・高さ・時刻〔複数都市〕／当日のタイムライン／延期・曇りのときの動き方／見学場・観察場所の比較表／スマホの具体的な設定／過去の実績〔出典つき〕）、図2つ以上、よくある質問、出典、更新履歴、主要な数字・日付・規則に「その文の中の」根拠リンク（機関名・ページ名の2〜8文字だけをリンクに。トップページで済ませない）、内部リンク（機体名→図鑑 `/rockets/…`、射場名→見学ガイド、撮り方→`/sky/smartphone/`、「まず結論」までに常設ガイドを1本）。
- **禁止事項**：確かめていない数字・日付・場所を書く／記憶で書く／体験の偽装／AI 画像を写真として扱う案／アフィリエイトのリンク・URL を作る／決まった一覧に無いタグ・カテゴリ／`events` やほかのカードを書き換える／修正の理由を本文の地の文に書く（更新履歴にだけ書く）／査読の基準を緩める。
- **出力（`articles/<ID>.draft`）**：`markdown`・`blocks`・`seo{title,description}`・`wp{category,tags,slug}`・`figures`・`updateChecklist`（T-7・T-3・T-1・当日・翌日。常設ガイドは3か月ごと）・`report`（構成／確かめた出典の表／計算した値／判断の分かれ目／運営者にお願いしたいこと／図の案・写真の案／関連〔未公開〕）。
- **完了条件**：自己点検を済ませ、`status: "査読中"`・`loop.state: "reviewing"` にして `jobs/review-<ID>-<round>` を査読に渡す。

### 4-3 査読・修正（reviewer。`review-manual.md`）

- **誰が何を見る**：作成とは別のセッションの査読エージェント（モデルは作成と同じ Opus 系で、トリガーが別）。主張を全部抜き出し、一次情報を自分で開き直し、曜日・時刻・方角をコードで計算し直し、今の状況を査読の時点で確かめる。**本文は書き換えない**（直すのは作成）。
- **直す範囲**：査読が出した P0・P1 を作成が全部直す（直せない指摘は理由と根拠 URL を `report` の冒頭に）。修正案は「文全体」で書く。「1回目の査読で、見つけられる P0・P1 はすべて出す。」小出しにしない。直っていない指摘は番号を変えずに再掲する。
- **再査読の条件**：不合格のたびに `jobs/article-<ID>-<round+1>` で書き直し→再査読。上限は `settings/reviewLoop.maxRounds`（現在 5。運営者が止めた記事を再開すると `loop.base` から数え直す）。上限に達すると `loop.state: "failed"` にして受信箱 `loopFailed`（受信箱担当が最大2回まで自動で再依頼→それでもだめなら見送り）。再査読では、指摘箇所に加えて日時・曜日・状況は毎回記事全体を見直す。

## 5. 査読基準

### 判定

運営マニュアル・手順書（原文）：

| 区分 | 定義 |
|---|---|
| **P0：公開を止める** | 時刻・日付・曜日・場所・今の状況の誤り。見え方の誇張（見えないものを見えると書く・街中でも理論値どおり見えると書く）。体験の偽装。捏造した数字・場所・リンク。安全に関わる抜け（日食の目の保護）。私有地・立入禁止区域を勧める |
| **P1：公開前に直す** | 一次情報で確かめていない数字。検索意図に答えていない。読者の時系列で詰まる点。ならではの要素が2つ未満。専門用語の説明なし。根拠リンクなし・リンク切れ。相対日付。要点ボックス・最終確認・出典・更新履歴なし。「推測」の書き忘れ。決まりにないタグ |
| **P2：改善** | 読みやすさ、表の形、言い回し、タイトル・説明文の長さ、同じ数字の重複、写真・図の案 |

- **A**：P0 0件・P1 0件。そのまま運営者の確認へ。**B**：P1 あり。直せば公開できる。**C**：P0 あり。公開保留。**D**：構成から作り直し。「P0 が1つでもあれば C 以下。判定は件数で機械的に行い、甘くも厳しくもしない。」
- 合格は A だけ。判定 → **合格（A）／要修正（B・C）／不合格（D＝作り直し。または上限回数で A に届かず `failed`）**。

### 公開不可にする条件（絶対に通さないもの）

- 曜日の誤り（1つでも P0）。世界時のまま書く。延期前の古い日時が残る。日本から見えない現象を「見える」と書く。体験の偽装。アフィリエイトの URL を作っている（印 `[AFF:…]` を置くだけが正しい）。見学場・駐車場・トイレ・規制を案内に無いのに案内している。私有地・立入禁止区域を勧める。日食の記事で目の保護が無い。エネルギー・原子力の話題（P1）。
- 手順書の「やってはいけないこと」：査読が A でない稿・運営者が止めた稿（`見送り`・`保留`・`loop.state` が `failed`）・アイキャッチが無い稿を入稿しない。

### よくある指摘とその直し方（実例）

## 10. 運用上の決まりごと

### 重複を避ける方法

- 記事：企画は既存カード（保留・見送りを含む）と見送り済みの企画を読み、同題材（同じイベント・場所・機材）は出さない。毎年のイベントは既存カードの年を更新する提案にする。同じ記事の同じ `kind` の依頼が `queued`・`running` なら、新しく作らない（`agent-jobs.md` 6）。
- イベント：同じ機体・号機、同じ天体現象（同じ流星群の同じ年）、同じ催しは足さない（イベント取得）。1つの変化に受信箱1件（公式ウォッチ）。
- SNS：直近60日の `posts` と同じ題材は NG（SNS 審査）。3つの SNS で同じ文面にしない。投票は週1回まで。Instagram は週2〜3回まで。
- リンクの再掲：**専用のルールは見当たりません（不明）。** 同じ内部リンクを繰り返さない、といった規定はない（教訓30のとおり、根拠リンクは「その文の中」に付けるため、同じ出典を複数回リンクすることは実際にある）。
- 受信箱：同じ対象・同じ趣旨の `open` があれば作らない。入稿の失敗は記事ごとに1件（同じ ID を上書き）。点検は1日1件にまとめる。
- 同じ失敗を毎時くり返さない：入稿は、直近が `error` で画像も稿も変わっていなければ再試行しない。

### 失敗・エラーが起きたときの対応

- 共通：ジョブを `error` にして原因を日本語で `message` に書く。「失敗を成功と書かない。」権限・WAF の拒否を、コマンドの形を変えて通そうとしない。
- 入稿：失敗したら `publish_wp.py` が元に戻す。受信箱 `publish-<ID>` に出す。403（WAF）は画像担当に作り直しを依頼。同じ記事で3回続いたら ownerOnly。
- 止まった依頼：点検が、`running` のまま60分以上更新なしを `error` に、`queued` のまま3時間以上を1回だけ起動し直す。同じ役割の `error` が24時間に3件以上なら受信箱に出す。
- 受信箱担当が1件ずつ自動で処理して閉じる（処理表は `inbox-manual.md`）。
- 利用上限：**直近、`USAGE_LIMIT_REACHED`（利用上限）で多くの定時実行が失敗している**（記事作成・査読以外の多数。2026-10-25〜28 に確認）。
- 停止・再開：アプリの `settings/agentPause`（`roles.<役割>.paused`）を各エージェントが最初に確認する。2026-10-26 に運営者の指示で全エージェントを停止し、10-28 11:30（日本時間）に再開した。**停止中の10-26〜28の間、停止フラグを書き込む場所を間違えたため、フラグは効いていなかった**（定時スケジュールの無効化だけが効いた。記事作成が 10-28 11:23 に1回走った記録あり）。次に止めるときは、`settings/agentPause` の `roles` の直下に直接書き、読み返して確かめること。

### 停止してオーナーに確認する条件

- 受信箱の `ownerOnly: true`：「認証情報・パスワード・鍵の入れ直し／お金・契約・規約／WAF・サーバー・外部サービスの設定の変更／運営者本人の経験・写真・好み」（`inbox-manual.md` 5。原文）。
- SNS：`approval: "owner"` の投稿（延期・結果・訂正・引用・写真の紹介）は運営者の確認まで予約しない。ブランドが 7609507 でない・空なら `inbox/sns-brand`、7372301 が見えたら審査を止めて `inbox/sns-brand-wrong`（ownerOnly）。
- 記事：査読が上限回数で A にならない（`loopFailed`）、企画の査定で不合格（`planReview`）、エージェントからの質問（`question`）で運営者しか知らないこと。
- 「迷ったら予約しない」「運営者にしかできないことを、推測で埋めて閉じない」。

### オーナーから受けた指示・禁止事項で、まだ有効なもの

運営マニュアル・手順書・このセッションの指示のうち、現在も有効と判断したもの：

1. 「このサイトはクロードで自動運転が基本設計です。現在のアプリ内通知ボックスに出ているものは全て自動で処理できるようにしてください。」→ 受信箱担当を追加。運営者に残すのは ownerOnly だけ。
2. 画像は AI の写真風にしない（アイキャッチは自作 CG、SNS は図解のみ）。
3. Metricool は miagetabi ブランド（7609507）のみ。KOAlil の ko（7372301）には触れない。X は Metricool に載せない。
4. 「SiteGuard Lite（WAF）はオンのままです。設定は変更しないでください。」（2026-10-24 の引き継ぎメモ）。→ WAF を回避しない（コマンドの形を変えて通そうとしない）。ただし運営者自身が一時停止・除外した事実がある（現状は不明）。
5. アイキャッチは「レパートリーはどんどん増やしていこう」（毎週の定期タスク）。
6. 全エージェントの一時停止→2026-10-28 11:30 再開（実施済み）。
7. Instagram・Threads の自動予約は、アプリの「自動で Metricool に予約する」を**オフのまま**（運営者が選択）。
8. 「エネルギー・原子力の話題は扱わない」（運営マニュアル）。
