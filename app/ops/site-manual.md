# サイト更新エージェント（siteupdate）の手順書

トップページ（ホーム）の「いま変わるところ」を、アプリの `events` と公式の最新情報に合わせて自動で更新する。**書き込んでよいのはホームの3か所だけ**（NEXT LAUNCH のカウントダウン・ティッカー・UPCOMING の表）。ほかのページ・記事・設定には触らない。

**書き換えてよいもの**：WordPress のホームの固定ページの上の3か所（`ops/site_home.py` が決まった場所だけを直す）、`sitebackups/home-<日時>`（直前のバックアップ）、受信箱 `inbox/site-…`、自分の `jobs/<ID>`
**書き換えないもの**：ホーム以外のページ・記事・テーマ・プラグイン・設定、`events`、`articles`、ほかのエージェントの持ち物

## 0. 共通
`ops/agent-jobs.md`（共通の約束。停止の確認を含む）と `ops/site-rules.md`（とくに 8「直前の更新」・12「ホームのカウントダウン」）を読んでから進める。道具は `ops/site_home.py` と `ops/home_countdown.py`（Artifact ツールの `read` で同じ場所に保存し、保存先のまま `python3` で実行。中身を書き写さない）。

## 1. いつ動くか
- 定時：毎朝（5時台）。過ぎた打ち上げ・イベントを表から外し、日付が決まったものを足す。
- 依頼：`kind: "siteupdate"`（公式ウォッチ・イベント取得が、打ち上げ・天体の日付や状況を変えたとき。運営者がアプリの「サイトを更新」を押したとき）。
- 変えるものが無ければ「変更なし」と報告してすぐ終わる。

## 2. 手順
1. 共通の手順で依頼を受け取る。
2. **一覧を作る**：`events` を全部読み、`pillar: "launch"` のものを `launches.json` にする（形は `ops/home_countdown.py` の先頭）。`guide`（図鑑ページの URL。無ければ空）・`official`（公式ページ。報道だけなら空）・`publicNote`（読者に見せる一文。**内部のメモは入れない**）・`rank` は、いまの `events`・公式ページ・既存の記事から決める。日付と時刻は `events` の値を、**作る直前に公式ページで確かめた値**にする（食い違えば公式を優先し、受信箱に1行）。
3. **UPCOMING の差分 `ops.json` を作る**（`ops/site_home.py` の先頭の形）：
   - `add`：今後120日以内の `events`（確定・予定。`launch` と `sky`）で、表にまだ無いもの。`small` は読者向けの一文（60字まで。日時・場所・見え方の要点。公式で確かめた事実だけ。「絶景」「必見」などは使わない。見え方は盛らない）。`star` は流星群なら見やすさの★（1〜5。月明かり・極大の時刻・天候の傾向から）、打ち上げなら「現地 / 中継」、特に勧めたいもの（運営者が `pick` に決めたものがあれば）は `PICK`。`guide` は、公開済みの記事（`articles` の `status` が `公開済み`）の URL がある題材だけ。`ticker` は英字の短い一文（例 `QUADRANTIDS — 01.04`）。
   - `edit`：日付・時刻・状況が変わったもの（延期など）。`match` に表の題名の一部。
   - `remove`：中止になったもの。
   - 過ぎた日の行は、スクリプトが自動で外す。
4. **差分を確かめる**：`python3 site_home.py plan launches.json ops.json`（公開ページを取って、差分を出すだけ）。外れる行・足す行・直す行が、2・3 の意図どおりか確かめる。意図しない行が消えるなら、`ops.json` を直す。
5. **反映する**（認証情報がある場合のみ）：`test -n "$MIAGETABI_WP_USER" && test -n "$MIAGETABI_WP_APP_PASSWORD"`（値は表示しない）。
   - ある → `python3 site_home.py apply launches.json ops.json`。スクリプトが、取得 → 書き換え → 検査（タグの対応・件数・変更の大きさ）→ 保存 → 公開ページで確認、までをし、確認に失敗したら**自分で元に戻す**。成功したら、カレントの `home-backup.json`（直前のバックアップ）を `sitebackups/home-<YYYYMMDDHHMM>` に `set` する（`raw` と `at` と `id`）。
   - 失敗（`NG:` が出た）・認証情報が無い → 6 に進む。**同じ失敗を何度も繰り返さない**（1回だけやり直してよい）。
6. **反映できなかったとき**：`plan --out new.html` で作った新しいホームの HTML は大きいので載せず、受信箱 `inbox/site-<YYYYMMDDHHMM>` を `set`：`{"kind": "change", "title": "ホームの更新（貼り替え）：<要点>", "body": "いま外れる行・足す行・直す行（箇条書き）。WordPress のホームの編集画面で、カウントダウンの <script>（id=\"mgCount\"）を次のものと入れ替え、UPCOMING の表を次のとおりに直してください。\n\n<script> 全体（home_countdown.py の出力）\n\n<li> の追加・変更（plan の差分）\n\n失敗の理由：<NG の文言（認証情報の値は書かない）>", "reason": "WordPress に自動で反映できなかったため", "status": "open", "by": "siteupdate", "createdAt": "<今>"}`。同じ内容の `open` があれば作らない。
7. 依頼を `done`（反映した）か `waiting`（受信箱に出した。`inboxId` を書く）にし、報告する（3行以内：反映した／受信箱に出した、外した行・足した行の数）。

## 3. してはいけないこと
- ホームの3か所以外を書き換えること。`apply` の検査を迂回すること（検査に落ちたら書かない）。
- 認証情報を表示・記録すること（db・ファイル・報告・受信箱に書かない。有無を確かめるなら `test -n` だけ）。
- 公式で確かめていない日時・数字を表に入れること。内部のメモ（`events.note` など）をそのまま読者向けの文にすること。
- 反映に失敗したのに「反映した」と報告すること。コマンドの形を変えて権限の拒否や WAF を通そうとすること。

## 4. 運営者に必要な準備（初回だけ）
- WordPress に、このエージェント専用のユーザー（権限は「編集者」。ホームの `<script>` を残すには `unfiltered_html` が要るため、保存後の確認で `<script>` が消えるなら「管理者」）を作り、「アプリケーションパスワード」を発行する。
- 環境の設定（クラウド環境の編集 → 環境変数）に `MIAGETABI_WP_USER`・`MIAGETABI_WP_APP_PASSWORD` を入れる。チャットには書かない。ホームの固定ページ ID が自動で見つからないときは `MIAGETABI_WP_HOME_ID` も。
- サーバーの WAF が REST API の書き込みを止める場合は、サーバー側で許可が要る（止められると `NG: … 403` になり、受信箱に貼り替え用の差分が出る）。
