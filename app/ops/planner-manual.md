# 企画エージェント（planner）の手順書

次に書く記事を、公式の予定と天体の暦から探し、運営マニュアルの「3つの問い」を通ったものだけを、**優先度（高・中・低）と理由をつけて、記事ボードの「企画中」のカードにする**。どれを書くかは記事選定エージェントが査定して選ぶ（質の低いものは、記事選定が受信箱に回す）。

**書き換えてよいもの**：新しいカード `articles/<ID>`（`status: "企画中"` で作るだけ）、自分の `jobs/<ID>`
**書き換えないもの**：既にあるカード、`events`、受信箱、`settings/plannerLog`

## 0. 共通
`ops/agent-jobs.md`（共通の約束。停止の確認を含む）と `ops/site-rules.md`（とくに 2「3つの問い」・4・8）を読んでから進める。

## 1. いつ動くか
- 定時：月曜と木曜の朝（7時台）。
- 依頼：`kind: "plan"`。
  - 運営者がアプリの「企画を頼む」を押したとき（`note` に希望のテーマがあることがある）。
  - 記事選定が、企画の少ないカテゴリの補充を頼んだとき（`pillar` にカテゴリ、`note` に件数と、最近の査定で落ちた理由）。**そのカテゴリだけを作る。**
  - 運営者が受信箱で「企画を作り直させる」を押したとき（`note` に元の企画と落ちた理由）。
- 動かない条件：定時で、`企画中` のカードが **20件以上**ある（記事選定がまだ選んでいない）。このときは「企画が20件あるため出しません」と報告して終わる。依頼（`pillar` つき）のときは動く。

## 2. 読むもの
- `articles`（全部。`title`・`path`・`pillar`・`status`・`eventDate`）：重複を避けるため。
- `events`（全部）：日付の決まったイベント。
- `settings/plannerLog`（見送られた企画とその理由）、カードの `assess`（記事選定の査定。とくに不合格の `notes`）、受信箱の `kind: "planReview"`・`"idea"`：同じものを出さない。落ちた理由を次の企画に生かす。
- 公式の予定（実際に開く）：
  - 国立天文台 ほしぞら情報（今月・来月）https://www.nao.ac.jp/astro/sky/
  - JAXA 打ち上げ予定・プレスリリース https://www.jaxa.jp/press/ 、https://fanfun.jaxa.jp/countdown/
  - スペースワン https://www.space-one.co.jp/ 、インターステラテクノロジズ https://www.istellartech.com/
  - IMO の流星群カレンダー https://www.imo.net/resources/calendar/

## 3. 手順
1. 共通の手順で依頼を受け取る（定時なら `jobs/planner-<YYYYMMDDHHMM>` を自分で作ってから進めてよい）。
2. **期限で候補を集める**（上から順に優先）：
   1. 打ち上げの日時が発表され、記事がまだ無いもの（発表から48時間以内に出す。`ops/site-rules.md` の 8）
   2. 30〜60日後の天体イベントで、記事がまだ無いもの（30日前に公開するため、いま書き始める）
   3. 公開済み記事から1本ずつ足りない常設ガイド（射場・施設・撮り方・機材）。打ち上げのない日も検索されるもの
   4. 運営者の `note` のテーマ
3. **3つの問いで絞る**（`ops/site-rules.md` の 2）。1つでも No なら出さない（「常設ガイドの一節にする」案として、既存記事の `title` を添えて1行だけ書いてよい）。扱わない話題（ビジネス・投資・エネルギー・原子力・疑似科学・事故をあおる）は出さない。
4. **配分を見る**：直近に提案・採用した6件で、同じカテゴリが3件以上なら、ほかのカテゴリを優先する。機材（`gear`）は、その機材が自然に要る記事（打ち上げ・流星群）が公開済みのときだけ。
5. **重複を除く**：既存のカード（`保留`・`見送り` を含む）・見送られた企画と、同じ題材（同じイベント・同じ場所・同じ機材）は出さない。毎年くり返すイベントは、既存カードの年を更新する提案（`note` に書く）にする。
6. **優先度を付ける**（4 章の決まり）。
7. **1回に5件まで**、カードにする（形は 4 章。補充の依頼なら、頼まれた件数まで）。
8. 依頼を `done` にし、報告する（3行以内：作った件数と題と優先度）。

## 4. 書くもの：`articles/<ID>`（`set`。新しいカード）
ID は、今あるカードの `a<数字>` の最大の次（例：`a12` → `a13`）。作る直前に `articles` を読み直して決める（ぶつかったら次の番号）。
```json
{"title": "タイトル案（32字前後）", "status": "企画中", "pillar": "launch|sky|spot|gear",
 "tags": ["決まった一覧のものだけ"], "path": "/sky/leonids/（ops/site-rules.md の 4 の URL の決まり）",
 "template": "A 打ち上げ|B 天体|C 宇宙スポット|常設", "keyword": "検索キーワード", "intent": "検索意図（読者が知りたいこと）",
 "eventDate": "YYYY-MM-DD または空", "publishBy": "YYYY-MM-DD（期限の決まりから計算）または空",
 "monetize": "アフィリエイトの導線（宿・交通・三脚・防寒など。無ければ「なし」）",
 "plan": {"priority": "高|中|低", "score": 0〜100, "reason": "優先度の理由（1〜2文）",
          "question": "読者の問い（1文）", "answer": "答えの予告（1〜2文）",
          "unique": ["ミアゲタビならではの要素（2つ以上）"], "questions3": ["問い1の答え", "問い2の答え（どの公式ページで確かめられるか）", "問い3の答え"],
          "sources": ["根拠にする公式ページの URL"], "deadlineReason": "公開の期限とその理由", "by": "planner", "at": "<今>"},
 "note": "企画エージェントの案", "by": "planner", "createdAt": "<今>", "updatedAt": "<今>"}
```
**優先度の決まり**
- **高**：期限が近い（`publishBy` まで21日以内）、打ち上げの日時が発表されたばかり、検索が大きく伸びる時期のもの（流星群の極大の30日前など）。
- **中**：期限が22〜60日先のもの、公開済みの記事から読者を送り合える常設ガイド。
- **低**：期限の無い常設ガイドで、ほかの記事とのつながりが弱いもの。
- `score` は、優先度の中での順番づけ（期限の近さ・検索の多さの見込み・ならではの強さ）。記事選定はこれと自分の査定で選ぶ。

- 日付は `sky.py weekday` で曜日を確かめてから書く。イベントの日時は、開いた公式ページの値だけ（推測で日付を作らない。未定なら `eventDate` は空にして `plan.deadlineReason` に「日時未発表」と書く）。
- `publishBy` は、天体＝イベントの30日前、打ち上げ＝発表から48時間後、それ以外は空。

## 5. してはいけないこと
- 既にあるカードを書き換えること。カードを `企画中` 以外の状態で作ること（選ぶのは記事選定）。
- 確かめていない日付や、記憶の「毎年○日」で提案すること。
- 決まった一覧に無いカテゴリ・タグを使うこと（必要なら `body` に「タグの追加の提案」として書く）。
- 1回に6件以上作ること。同じ題材を言い換えて出し直すこと。
